Building a Centralized Log Server for FortiGate — Graylog, Field Parsing, and a Live Security Dashboard

fortigate graylog opensearch siem

A FortiGate firewall generates a huge amount of useful traffic and security data, but by default that data only lives on the box itself, in a small local buffer, until it gets overwritten. If you don't have FortiAnalyzer licensed, there is no easy way to search last week's traffic, build a dashboard, or get alerted the moment someone starts hammering your management interface with login attempts. So I built a small, self-hosted log server using Graylog, OpenSearch, and MongoDB — free and open-source stack — to receive FortiGate syslog, parse it into proper fields, and put a live security dashboard on top of it.

This post is the step-by-step version of that setup: standing up the log server, pointing the FortiGate at it, parsing the raw messages into searchable fields, running searches, and finally building the dashboard itself. 

architecture
FortiGate ──UDP 5140──► Graylog Raw Input ──► Pipeline (field parser) ──► OpenSearch
                                                                            │
                                                                     Dashboards / Search
Note on IPs and credentials: every hostname below is written as fixthestack.local (my log server) — substitute your own server's address. Login credentials, API keys, and real source IPs from any incident are intentionally left out; the queries and payloads shown are structural examples only.

The stack, at a glance

ComponentVersionRole
Ubuntu Server24.04 LTSHost OS for the log server
MongoDB8.0Stores Graylog's own config — inputs, users, dashboards
OpenSearch2.19.6Stores and indexes the actual log messages
Graylog6.2Receives syslog, runs the parsing pipeline, serves search + dashboards

Minimum 4 GB RAM works for a lab; 8 GB+ is what I'd recommend for anything that's actually going to carry production FortiGate traffic, since both OpenSearch and Graylog run on the JVM and want their own heap.

Part 1 — Building the log server

1. System preparation

bash
apt-get update && apt-get upgrade -y
apt-get install -y apt-transport-https curl gnupg2 ca-certificates wget lsb-release pwgen

2. Install MongoDB

Graylog 6.2 needs MongoDB 8.0 — the older 7.0 line doesn't ship a repository for Ubuntu 24.04 (noble) yet. 

bash
curl -fsSL https://www.mongodb.org/static/pgp/server-8.0.asc | \
  gpg --dearmor -o /usr/share/keyrings/mongodb-server-8.0.gpg

echo "deb [ arch=amd64,arm64 signed-by=/usr/share/keyrings/mongodb-server-8.0.gpg ] \
  https://repo.mongodb.org/apt/ubuntu noble/mongodb-org/8.0 multiverse" \
  > /etc/apt/sources.list.d/mongodb-org-8.0.list

apt-get update
apt-get install -y mongodb-org
systemctl enable --now mongod

Verify:

bash
mongosh --eval "db.adminCommand('ping')"

Expect { ok: 1 } back.

3. Install OpenSearch

bash
curl -fsSL https://artifacts.opensearch.org/publickeys/opensearch.pgp | \
  gpg --dearmor -o /usr/share/keyrings/opensearch-keyring.gpg

echo "deb [signed-by=/usr/share/keyrings/opensearch-keyring.gpg] \
  https://artifacts.opensearch.org/packages/2.x/apt stable main" \
  > /etc/apt/sources.list.d/opensearch-2.x.list

apt-get update
apt-get install -y opensearch

Edit /etc/opensearch/opensearch.yml for a single-node setup:

yaml
cluster.name: graylog
node.name: node-1
path.data: /var/lib/opensearch
path.logs: /var/log/opensearch
network.host: 127.0.0.1
http.port: 9200
discovery.type: single-node
plugins.security.disabled: true
action.auto_create_index: false

Set the JVM heap to roughly half of available RAM in /etc/opensearch/jvm.options:

bash
-Xms2g
-Xmx2g

bash
systemctl enable --now opensearch

Verify:

bash
curl -s http://127.0.0.1:9200/_cluster/health?pretty

Look for "status" : "green" (or "yellow" — see the troubleshooting note below).

4. Install Graylog

bash
wget -qO - https://downloads.graylog.org/repo/debian/pubkey.gpg | \
  gpg --dearmor -o /usr/share/keyrings/graylog.gpg

echo "deb [signed-by=/usr/share/keyrings/graylog.gpg] \
  https://downloads.graylog.org/repo/debian/stable 6/ /" \
  > /etc/apt/sources.list.d/graylog.list

apt-get update
apt-get install -y graylog-server

Graylog needs two secrets in its config: a random password_secret used to salt sessions, and a SHA-256 hash of your chosen admin password for root_password_sha2. Generate both yourself rather than reusing anything from a guide: 

bash
# 96-character random secret
pwgen -N 1 -s 96

# SHA-256 hash of your chosen admin password
echo -n "<your-chosen-password>" | sha256sum | cut -d' ' -f1

Edit /etc/graylog/server/server.conf:

ini
password_secret = <output of pwgen above>
root_password_sha2 = <output of the sha256sum above>
http_bind_address = 0.0.0.0:9000
elasticsearch_hosts = http://127.0.0.1:9200
mongodb_uri = mongodb://localhost/graylog

bash
systemctl enable --now graylog-server

Give it about 60 seconds to come up, then verify:

bash
systemctl status graylog-server

Log in to the web UI at http://fixthestack.local:9000 with the admin username/password you set above.

5. Firewall rules

bash
ufw allow 22/tcp    # SSH — add this BEFORE enabling UFW
ufw allow 9000/tcp  # Graylog web UI + API
ufw allow 5140/udp  # Syslog input for FortiGate
ufw --force enable
Careful: always allow port 22 before running ufw enable, or you'll lock yourself out of the server over SSH.

6. Verify everything is up

bash
systemctl status mongod opensearch graylog-server
ss -tlnup | grep -E '27017|9200|9000'
curl -s http://127.0.0.1:9200/_cluster/health | python3 -m json.tool

Part 2 — Mapping the log server on FortiGate

1. Create the syslog input in Graylog

Via the web UI:

  1. Go to System → Inputs
  2. Select Raw/Plaintext UDP, click Launch new input
  3. Title: FortiGate Syslog; Bind address: 0.0.0.0; Port: 5140
  4. Click Save

2. Point the FortiGate at the log server

On the FortiGate CLI:

fortios
config log syslogd setting
    set status enable
    set server fixthestack.local
    set port 5140
    set facility local0
    set format default
end

Verify:

fortios
show log syslogd setting

output
config log syslogd setting
    set status enable
    set server "fixthestack.local"
    set port 5140
    set mode udp
    set facility local0
    set format default
end

3. Confirm logs are actually arriving

On the log server, watch the UDP port directly:

bash
sudo tcpdump -i any -n udp port 5140 -c 10

Or check from the Graylog UI: go to Search, set the time range to Last 5 minutes, and click Search — FortiGate messages should start showing up.

A typical raw FortiGate traffic log looks like this before parsing:

raw

Part 3 — Parsing the raw logs into fields

Right now every FortiGate log is just one long unstructured string — you can full-text search it, but you can't group by source IP or sum bytes transferred. That needs a Processing Pipeline that extracts each key=value pair into its own Graylog field.

I built one pipeline, "FortiGate Field Parser," with one rule per field — about 34 rules in total — connected to the Default stream so it runs on every incoming message. A few syntax notes for Graylog's rule language (GPL), since it isn't quite regular regex:

  • Use [^ ]+ instead of \S+ — the \S shorthand isn't supported
  • Use [0-9]+ instead of \d+ — same reason
  • Quoted values: field="(?<val>[^"]+)"; unquoted values (IPs, ports): field=(?<val>[^ ]+)
  • Numeric fields must go through to_long() to be stored as a proper number in OpenSearch, not a string

Two representative rules — a quoted string field, and a numeric one:

gpl
rule "fg_action"
when
  contains(to_string($message.message), "action=")
then
  let m = regex("action=\"(?<val>[^\"]+)\"", to_string($message.message));
  set_field("action", m["val"]);
end

gpl
rule "fg_sent_byte"
when
  contains(to_string($message.message), "sentbyte=")
then
  let m = regex("sentbyte=(?<val>[0-9]+)", to_string($message.message));
  set_field("sent_byte", to_long(m["val"]));
end

Gotcha — index field type: if sent_byte/rcvd_byte show up as strings in OpenSearch (breaking sum() widgets on the dashboard), OpenSearch locked in the wrong type from the first message it ever saw for that field, before to_long() was added to the rule. Fix: rotate the index so it starts a fresh mapping — System → Index Sets → Default index set → Maintenance → Rotate active write index — then give it ~60 seconds for new messages to land with the correct numeric type.

Adding or testing a rule

  1. Go to System → Pipelines → FortiGate Field Parser, click Edit on the stage, add the rule, click Update stage
  2. To test one without waiting for a real message: System → Pipelines → Simulator, paste a raw FortiGate line, and see exactly which fields get extracted

Part 4 — Checking the logs

With fields in place, the Search page becomes genuinely useful. A few queries I use regularly:

QuestionQuery
Who's failing to log in?action:login AND status:failed, grouped by srcip
Who's logging in successfully?action:login AND status:success
What's my top traffic source?(all messages), grouped by srcip, sorted by sum(sent_byte) desc
Is a given IP being blocked?srcip:<ip> AND action:deny, last 1 hour
What countries are connecting?(all messages), grouped by src_country

Click Open in Search from any dashboard widget to jump straight into the full search view with that widget's query already filled in — handy for going from "this number looks odd" to the individual log lines behind it.

Building a widget, step by step

  1. Open a search with the query and time range you want (e.g. action:login AND status:failed, last 24 hours)
  2. Click Create new → Aggregation
  3. Pick the visualization type — Single Number, Data Table, Line Chart, or Bar Chart
  4. Set Row pivot to the field you want to group by (e.g. srcip), or leave it empty for a single number
  5. Set the metric — count(), sum(field), etc.
  6. Save the widget, then drag it onto your dashboard and resize/reposition as needed
Tip — drilling down: clicking a row in a Data Table widget (say, an IP in "Top Source IPs") filters the whole dashboard down to that value, so you can go from a high-level count straight to "show me everything from this one address" in one click.

Default time range on mine is Last 24 hours, changeable from the clock icon in the top-right of the dashboard — presets for 1 hour, 24 hours, 7 days, or a custom range.

Bonus — alerting on brute force attempts

Once the fields exist, alerting is a natural next step rather than extra work. An Event Definition watching failed logins:

  1. Go to Alerts → Event Definitions → Create
  2. Condition type: Filter & Aggregation
  3. Search query: action:login AND status:failed, grouped by srcip
  4. Aggregation condition: count() > 10, time window: 5 minutes
  5. Add a notification — email or a webhook (Slack, etc.)

A couple more thresholds worth having from day one:

AlertQueryThreshold
Brute forceaction:login AND status:failedcount > 10 / 5 min
High outbound traffic(all traffic)sum(sent_byte) > 1 GB / 1 hour
Policy violation spikeaction:denycount > 1000 / 15 min

Housekeeping — retention and backup

Log volume adds up fast, so retention needs a decision, not a default. Under System → Index Sets → Default index set, I set rotation to daily and retention to delete indices past 30 days.

Two things worth backing up regularly — pipeline rules and the dashboard definition itself:

bash
# Pipeline rules
curl -s -u <user>:<password> http://fixthestack.local:9000/api/system/pipelines/rule \
  > pipeline-rules-backup-$(date +%Y%m%d).json

# Dashboard
curl -s -u <user>:<password> \
  http://fixthestack.local:9000/api/views/<dashboard-id> \
  > dashboard-backup-$(date +%Y%m%d).json

# Full Graylog config (MongoDB)
mongodump --db graylog --out /backup/graylog-$(date +%Y%m%d)/

Wrapping up

End to end, this gives a FortiGate a proper searchable log history and a live dashboard without needing a FortiAnalyzer license — install the stack, point the firewall at it, parse the raw syslog into fields, then build search-backed widgets on top. The same pattern extends easily to other syslog-speaking devices; only the pipeline rules for field extraction would need to change.
